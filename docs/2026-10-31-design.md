## 範圍

**做**：

- 一份乾淨的基準韌體：搖一下板子 → LED 依規則閃；拍手 → LED 切換（實際行為在 Task 2 定）
- 3–5 個埋好的 bug，每個一個資料夾：bug patch、白話 bug 描述、人寫的驗收檢查
- 主機端流程：選 bug → 套 patch → AI 理解 → AI 修 → 閘門 → 編譯 → 燒錄 → 板子驗證 → 不過就分類失敗原因再修（最多 N 次）→ AI 一句話解說
- 狀態網頁：每一關的狀態、每一步用的模型和成本、挑 bug 的按鈕
- README：安裝、操作步驟、AI 使用方式、限制、第三方來源

**不做**（除非進度超前）：

- 觀眾自己描述新功能（驗收只能由 AI 寫，違反主軸）
- 手機掃 QR 投票（第 4 週再決定）
- 攝影機數閃燈（第 3 週再決定）
- 其他板子（目前只支援 Nano 33 BLE Sense Rev2）

## 流程

```
[按鈕挑 bug] → 套 bugs/<id>/bug.patch 到乾淨的基準韌體副本
   → ① 理解：MixRoute 把白話描述整理成「現象／預期／可能位置」
   → ② 修：Claude Code headless，只能讀寫工作區的韌體檔
   → ③ 閘門：diff 只能碰允許的檔，碰到鎖住的檔或 diff 太大 → 擋下，算失敗
   → ④ 編譯：arduino-cli compile
   → ⑤ 燒錄：arduino-cli upload
   → ⑥ 驗證：照 bugs/<id>/check.json 提示「請搖一下」→ 讀序列埠事件 → 對預期
   → 不過：⑦ MixRoute 分類失敗原因（編譯錯／行為不對／被閘門擋）→ 帶著原因回 ②，最多 N 次
   → 過了：⑧ MixRoute 用一句話向觀眾解釋修了什麼
```

## 驗證與閘門（主軸）

- **鎖住的檔**：序列埠回報模組（例 `report.h`／`report.cpp`）和所有 `bugs/*/check.json`。AI 改動的 diff 只要碰到其中一個 → 直接判失敗，不編譯、不燒錄。
- **允許的檔**：只列 bug 所在的應用程式檔；其他路徑一律擋。
- **diff 大小上限**：避免「整個重寫一份」繞過檢查。
- **驗收由人寫**：`check.json` 寫「要給什麼刺激（請搖一下／拍手）」和「序列埠要看到哪些事件、次數、時間範圍」。AI 讀不到驗收內容的話更好（Task 5 決定要不要藏起來）。
- **已知限制**（照實寫進 README）：回報模組和被修的程式跑在同一塊板子上，獨立性靠閘門保證，不是物理隔離；攝影機見證就是為了補這一點。
