### Task 1：工具鏈（約 3 小時）

- [x] 裝 arduino-cli 1.5.1 和核心 `arduino:mbed_nano` 4.6.0；`board listall` 確認 FQBN 是 `arduino:mbed_nano:nano33ble`
- [x] 裝 Rev2 的 IMU 函式庫 `Arduino_BMI270_BMM150` 1.2.4（datasheet ABX00069：IMU 是 BMI270＋BMM150，不是 Rev1 的 LSM9DS1）
- [x] 用一支 blink 跑一次：compile → upload → 用 pyserial 讀到序列埠輸出

**驗收**：一行指令完成「編譯＋燒錄＋讀到 `READY`」，把那行指令和實際輸出記進 README 草稿。
✅ 2026-11-02：連跑 10 次 10/10 通過（每輪約 13 秒：編譯約 5 秒、燒錄約 7 秒），從燒錄模式開始也通過。修掉了兩個會讓燒錄時好時壞的問題，原因寫在 `loop/flash_check.py` 的 `enter_bootloader()` 和 `open_board()`。

### Task 2：基準韌體＋鎖住的回報模組（約 5 小時）

- [ ] `firmware/base/`：搖一下 → LED 照規則閃；拍手 → LED 切換（實際規則在這一步定）
- [ ] `report.h`／`report.cpp`：每個事件印一行固定格式，例 `EVT,<ms>,SHAKE` 和 `EVT,<ms>,LED,ON`。所有 LED 動作都要經過回報模組，不能直接寫腳位
- [ ] 開機印 `READY,<firmware id>`

**驗收**：搖 3 次、拍手 2 次，序列埠的事件數和實際動作一致，人工核對 3 輪都一致。

### Task 3：bug 組合＋檢查程式（約 5 小時）

- [ ] 格式：`bugs/<id>/bug.patch`、`bugs/<id>/ticket.md`（白話描述，像使用者回報）、`bugs/<id>/check.json`（刺激提示＋預期事件＋時間範圍）
- [ ] 先做 3 個 bug，種類要不同（例：次數錯、門檻錯、狀態沒重置），每個都要外行人看得出差別
- [ ] `loop/check.py <bug id>`：印出刺激提示 → 讀序列埠 → 和 `check.json` 比對 → PASS／FAIL 加上原因

**驗收**：每個 bug 套上 patch 後 `check.py` 判 FAIL；在基準韌體上判 PASS。3 個 bug × 2 種狀態，總共 6 次，全部判對。

### Task 4：修 bug 流程（約 6 小時）

- [ ] `loop/run.py <bug id>`：複製基準韌體到工作區 → 套 patch → `claude -p`（只給工作區路徑、只准用讀寫檔的工具、不給 shell）→ compile → upload → `check.py`
- [ ] 每一步把狀態和耗時寫進 `runs/<時間>/status.json`，T7 的網頁讀這個檔

**驗收**：3 個 bug 各跑 3 次，共 9 次，至少 7 次由 `check.py` 判 PASS；每次的 `status.json` 都完整。

### Task 5：閘門（約 3 小時）

- [ ] 允許清單：每個 bug 只准改它所在的檔
- [ ] 鎖住的檔：碰到 `report.*` 或任何 `check.json` → 判失敗，不編譯
- [ ] diff 行數上限
- [ ] 決定要不要讓 AI 看不到 `check.json`（看得到比較容易修，看不到才符合「驗收由人掌握」），把理由寫進設計規格

**驗收**：手工做 3 份壞 diff（改 `report.cpp`、改 `check.json`、超過行數上限），閘門全部擋下，而且沒有進到編譯。

### Task 6：重試＋計時（約 3 小時）

- [ ] 失敗時把原因（編譯錯誤摘要、閘門原因、`check.py` 的差異）帶進下一次修，最多 N 次（先設 3）
- [ ] 量一輪的時間：理解、修、編譯、燒錄、驗證各花多久

**驗收**：用一個「第一次常修錯」的 bug 示範重試後成功；記下 9 次執行的時間中位數。**11/15 停損在這裡判斷。**

### Task 7：狀態網頁＋挑 bug 按鈕（約 4 小時）

- [ ] 每個 bug 一個按鈕，按下就跑 `run.py`；同時只准跑一輪
