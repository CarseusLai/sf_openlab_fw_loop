### Task 2：基準韌體＋鎖住的回報模組（約 5 小時）

- [x] `firmware/base/`：搖一下（> 2.5 g，600 ms 內不重複計）→ 橘燈快閃 3 下後回到原狀態；**翻面朝下**（z < −0.7 g 持續 300 ms）→ 橘燈切換亮／暗。門檻來自 `firmware/calibrate` 量測：靜止 1.01 g、拿起放下 < 1.5 g、用力搖 > 4 g；正面朝上 z = +1.01 g
- [x] `report.h`／`report.cpp`：`EVT,<ms>,SHAKE|FACE_DOWN|FACE_UP` 和 `EVT,<ms>,LED,ON|OFF`；LED 只能經 `report_led()` 改，且只有狀態真的改變才算事件
- [x] 開機印 `READY,<firmware id>`

**驗收**：搖 3 次、拍手 2 次，序列埠的事件數和實際動作一致，人工核對 3 輪都一致。
✅ 2026-11-05（調整後的標準）：搖 3 下兩次都 3/3（每下 6 次燈變化）；翻面朝下 2/2、朝上 2/2，燈照規則切換；多次靜止都沒有誤觸發。**沒驗到**：搖晃＋翻面交錯做 3 輪（嗶聲定時提示人跟不上，改由 Task 3 的 `check.py` 一步一步提示補驗）。

**決策與未決**：
- 拍手改成翻面（2026-11-05 使用者決定）：拍手偵測不穩，展示現場的噪音也會誤觸發。觀察到的現象（推論，未證實）：用力搖過之後麥克風靈敏度大降（拍手峰值從約 15000 掉到 < 110），重新燒錄後才恢復；PDM 取樣率全程穩定在 16 kHz。要再用麥克風之前，先做「重開機 → 拍 3 → 搖 3 → 拍 3」對照實驗
- 板子在主機沒開序列埠時送出的事件會丟掉 → `check.py` 必須先開好序列埠、確認連上，才提示人做動作
- 第一版韌體曾在正面朝上靜止時報過一次 `FACE_DOWN`，之後兩次燒錄都重現不出來；若再出現，看當下的 z 值

- [x] 格式：`bugs/<id>/bug.patch`、`bugs/<id>/ticket.md`（白話描述，像使用者回報）、`bugs/<id>/check.json`（每一步：要念的提示、觸發事件、等多久、觸發後看多久、預期的事件數或燈的狀態）
- [x] 3 個 bug，各改 `app.cpp` 一行：b1 次數錯（只閃 2 下）、b2 單位錯（門檻寫成 m/s²，怎麼搖都沒反應）、b3 狀態沒重置（燈亮著時搖，閃完熄掉）
- [x] `loop/check.py <check.json> <sketch>`：燒錄 → 序列埠全程開著 → **用中文語音念提示**（Microsoft Hanhan Desktop）→ 偵測到觸發事件才往下 → PASS／FAIL 加原因；`loop/make_variant.py <id>` 產生 `work/<id>/base`；判斷邏輯有單元測試 `tests/test_check.py`

**驗收**：每個 bug 套上 patch 後 `check.py` 判 FAIL；在基準韌體上判 PASS。3 個 bug × 2 種狀態，總共 6 次，全部判對。
✅ 2026-11-05：5/5 判對（b1、b2 的驗收內容相同，基準版只跑一次）。FAIL 原因各自對中 bug：「LED,ON 預期 3 次，實際 2 次」「等了 20 秒沒偵測到 SHAKE」「第 3 步：燈預期 ON，實際 OFF」。每項 19–37 秒。b3 的基準版那次同時補驗了 Task 2 的「搖晃＋翻面交錯」。
- 學到：人跟不上固定時間點的嗶聲；改成「念一句、等到動作發生才往下」就一次跑完。Task 7 的網頁也照這個方式提示

### Task 4：修 bug 流程（約 6 小時）

- [x] `loop/run.py <bug id>`：複製基準韌體到工作區 → 套 patch → `claude -p`（只給工作區路徑、只准用讀寫檔的工具、不給 shell）→ compile → upload → `check.py`
- [x] 每一步把狀態和耗時寫進 `runs/<時間>/status.json`，T7 的網頁讀這個檔；AI 的 diff 存 `fix.diff`、回覆存 `reply.json`
- 修 bug 的 AI：`claude -p --model sonnet --tools Read,Edit,Glob,Grep --permission-mode acceptEdits`，關掉 hook、MCP、使用者設定；**工作區放在 repo 外的暫存資料夾**，因為 repo 的 `CLAUDE.md` 連到擁有者的整套 agent 規則，放在 repo 裡會一起被載入。指示在 `loop/fix_prompt.md`

**驗收**：3 個 bug 各跑 3 次，共 9 次，至少 7 次由 `check.py` 判 PASS；每次的 `status.json` 都完整。
✅ 2026-11-06：**9/9 PASS**。修的時間中位數 8.3 秒（7.2–9.4），每次約 US$0.023–0.026，9 次共 US$0.22；燒錄＋驗收 36–62 秒。另外查過 9 個工作區：`report.*`、`base.ino`、`app.h` 都沒被改，沒有新增檔案，每次只改 1 行，而且都是根因（b2 改回 2.5 並註明「IMU 回報的單位是 g」）。
- 注意：3 個 bug 都很簡單，AI 每次第一次就修對，**重試的路徑還沒被跑到過**（Task 6 要刻意做一個第一次常修錯的 bug）
- 2026-11-06 b2 的 patch 原本留了註解 `// 2.5 g in m/s^2`，等於把答案告訴 AI → 已拿掉；b2「AI 看懂單位錯」的結論要打折扣
- 2026-11-06 b4（症狀在閃燈、原因在翻面偵測 `FACE_HOLD_MS = 0`）：驗收 4/4 判對，包含「閃完一律熄燈」這個錯誤修法也會在翻面那步被抓到；但 AI 修 3 次都直接找到真正原因，**「板子推翻 AI」仍未發生**

**2026-11-09 動作見證與編譯快取**：
- 讀 IMU 移到鎖住的 `base.ino`，它自己回報 `EVT,<ms>,MOTION,<最大 g>`（> 1.5 g 開始、< 1.2 g 持續 300 ms 結束）；`app.cpp` 只收 `app_loop(fresh, x, y, z, now)`
- `check.py` 三種結果：PASS／FAIL（有 MOTION 卻沒觸發 → 韌體的錯，並報出最大 g 值）／RETRY（逾時都沒 MOTION → 人沒動，請重做）；語音改成背景播放，念提示時也在讀序列埠
- 實測：b2 被搖 → FAIL「板子有被動到（最大 5.8 g），但韌體沒有回報 SHAKE」；b2 不碰 → RETRY 2/2
- **編譯快取的坑**：arduino-cli 依 sketch 路徑快取，同路徑檔案改過後會用到過期產物——b2 不碰時每 2.8 秒假報 4.57 g，`--clean` 後消失（4/4 → 0）。`flash()` 改成依原始碼內容雜湊決定 `--build-path`，燒錄用 `--input-dir` 指定同一處
- 輕輕搖 5 次的 MOTION 最大值：1.52、1.61、1.93、1.69、2.24 g（跟拿起放下的 1.3–1.5 g 很接近，「輕搖才觸發」的 bug 門檻空間太窄，不採用）
- 展示素材：AI 修完自己說「我沒辦法編譯或燒錄，所以這個修改還沒在板子上測試過」，之後板子才判 PASS
